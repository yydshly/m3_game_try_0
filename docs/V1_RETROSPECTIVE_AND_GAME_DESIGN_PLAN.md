# AI 小镇生活 V1 复盘与后续游戏设计规划

> 本文档是 AI 小镇生活 V1 原型的项目复盘。语气为工程化反思，不是宣传稿。结论是：V1 成功完成技术探索，但不应直接进入功能堆叠式 V2。

---

## 1. 项目初始目标

本项目最初的目标不是做一款传统经营游戏，而是验证一个核心假设：

**MiniMax-M3 能否在游戏世界中承担规划者、事件导演、广播员和记忆引用者的角色，而不仅仅是生成 NPC 对话。**

具体来说，V1 试图验证以下链路能否在轻量 Web 原型中跑通：

```
居民有状态（体力、心情、记忆）
  → AI 规划居民行动
    → 舞台动画呈现行动
      → AI 生成事件
        → 玩家做选择
          → 选择影响居民和小镇
            → 小镇记住选择
              → 后续广播/事件/对话引用过去状态
```

这个目标已经达成。V1 是一个技术探索，不是游戏产品。

## 3. V1 已验证的 AI 游戏闭环

V1 验证了一个完整的轻量 AI 游戏闭环：

```
居民状态（体力、心情、记忆）
  → AI 规划居民行动
    → 舞台动画呈现
      → AI 生成事件
        → 玩家做选择
          → 小镇记住选择
            → 后续广播/事件/对话引用状态和记忆
```

**MiniMax-M3 在 V1 中的角色（已验证）：**

- **规划者** — AI Director 根据小镇状态 + 记忆选择生活场景，安排居民任务
- **叙事导演** — M3 生成小镇事件，包含标题、文案、地点、涉及居民、选项
- **广播员** — M3 生成小镇广播文案与音乐氛围提示词
- **记忆引用者** — buildPromptMemoryNarrative 将选择记忆和居民记忆注入 prompt

**V1 的核心结论：** 在轻量 DOM/Web 原型中，M3 可以驱动一个完整的"规划→演出→事件→选择→记忆"游戏循环，而不仅仅是生成 NPC 对话。这是 V1 的探索价值所在。

## 当前项目进展总结

**V1 已经完成 AI 小镇生活的技术探索，已跑通完整可玩闭环。**

当前项目可以作为参考样机，不适合继续直接堆功能。后续若继续，应先做游戏设计，不应直接进入 V2 开发。

当前项目的核心价值不是"已经做成一个完整游戏"，而是证明了 **AI 可以进入游戏世界的规划、事件、广播、选择反馈和记忆链路**。这是 V1 作为技术探索的交付物。

## V1 后期关键体验修复

V1 后期围绕"玩家能感到小镇在回应自己"这一目标，修复了多项体验问题：

| 修复项 | 意义 |
|--------|------|
| 任务完成反馈增强 | 头顶徽章 + 右侧面板状态，让玩家看到行动有结果 |
| 小镇广播 TTS 探索 | 验证了 MiniMax TTS 可用于广播语音合成 |
| 广播/事件引用 townMemory | 居民对话可以引用近期记忆，世界感更强 |
| 居民状态和表情反馈 | 心情表情变化让居民更像"活的" |
| 地点特效修复 | bloom / steam / spark 等动画让地点有呼吸感 |
| 人物对白气泡截断修复 | 对白完整显示，不因宽度被切 |
| 对话顺序修复 | 移除 rotationSeed 对 snippets 的整体轮转，保持问答语义稳定 |
| 点击居民观察反馈确认 | 心情表情、关系状态、近期记忆让交互有回应感 |

**这些修复让原型从"AI 能生成内容"推进到"玩家能感到小镇在回应自己"。**

## 为什么现在停止继续开发是正确的

**技术验证已经完成。** V1 验证了 M3 可以作为规划者、事件导演、广播员和记忆引用者。这个目标已达成，继续堆功能不会产生新的核心认知。

**继续堆功能会掩盖真正问题。** 如果继续在 V1 上加 TTS、加对话、加音乐，问题不会被解决，只会被更大的代码量掩盖。

**真正瓶颈已经变成游戏设计。** 玩家每天为什么回来？居民为什么值得关心？这些不是技术问题，是设计问题。技术验证完成之后，继续堆技术不会回答这些问题。

**现有代码有原型技术债。** render.js 过重、状态边界不清、缺少状态机。在有技术债的代码上继续开发，会持续遭遇架构摩擦，最终得到一个更贵的原型而不是一个更好的游戏。

**现在停止不是放弃，而是避免把一个成功的技术验证原型拖成一个不可维护的半成品。**

## 下一次 AI 游戏开发前应准备的设计资产

在进入任何开发之前，建议先完成以下设计资产：

```
游戏一句话概念
玩家身份（玩家是谁，在这个世界里扮演什么角色）
世界观设定（小镇的地理、气候、社会状态）
核心情绪关键词（治愈？陪伴？挑战？成长？）
一天主循环（玩家一天做什么？什么是"一天"的闭环？）
一周/一季节奏（短循环是什么？长循环是什么？）
居民设定表（每位居民的名字、性格、习惯、愿望）
居民关系图（居民之间有什么关系？谁和谁是朋友？）
长期目标（玩家有目标吗？目标是什么？）
事件导演规则（AI 事件导演的边界在哪里？）
记忆影响规则（小镇记忆如何影响未来事件？）
AI 生成边界（哪些内容由 AI 生成，哪些必须由规则控制？）
非 AI 规则边界（哪些必须由规则决定，不让 AI 随意生成？）
MVP 功能清单（第一个可玩版本需要哪些功能？）
技术架构草案（用不用游戏引擎？状态管理方案？）
```

## 4. 做对了什么

从产品和技术两个角度反思，V1 的成功点包括：

**产品决策：**

1. 没有一开始就上游戏引擎（Phaser/Pixi/Canvas），而是用轻量 Web 原型快速验证核心假设
2. 先验证 AI 驱动闭环，而不是先做复杂美术和数值体系
3. 居民状态、任务、事件、选择、记忆形成了最小世界感——玩家感受到小镇在"记得"
4. 玩家选择被写入 townMemory，小镇记忆链路让玩家感受到世界在回应自己
5. 点击居民后的观察反馈让世界变得更可交互，而不是单向展示
6. 选择了合适的验证深度：不是 MVP 式的功能残缺，也不是完整游戏式的过度投入

**工程实现：**

7. 测试脚本逐步覆盖了关键体验回归，无需手动测试
8. domain 层与 DOM 层分离，domain 逻辑可以在 Node.js 中独立运行
9. MiniMax API fallback 设计：无 API Key 时仍可运行完整闭环
10. UI 状态和游戏状态有一定分离，通过 uiState 控制动画锁步

## 5. 暴露的问题与技术债

以下问题不是简单 bug，而是原型阶段自然产生的技术债，需要在下一项目早期设计中规避：

**架构层面：**

- `render.js` 逐渐变重，承担了 UI 渲染、动画调度、状态计算多种职责
- UI 状态（uiState）、游戏状态（state）、演出状态（isAnimating）边界不够清晰
- 缺少统一状态机，演出逻辑（travel → task → feedback）依赖时间顺序的隐式约定

**游戏机制层面：**

- 对话、事件、记忆、任务之间是轻量拼接，不是系统化游戏机制
- 很多体验通过补丁式规则修正（如对话顺序修复、地点特效修复）
- 缺少真正意义的游戏主循环——玩家目标是什么，一天完成后意味着什么
- 缺少长期目标：玩家没有理由在第一天之后继续第二天
- 缺少居民关系成长系统：关系数值存在，但不影响行为和剧情
- 缺少故事结构：事件是随机散乱的，没有叙事弧线

**AI 输出层面：**

- M3 生成的事件和广播质量依赖 prompt，缺少强导演规则约束
- AI 输出有时偏离小镇氛围，需要频繁 prompt 调整

**资产层面：**

- 地图和人物表现仍是 DOM/SVG 原型级，不是美术级资产
- 对话是模板/轻生成混合，不是完整自由对话

这些问题不是 V1 的失败，而是原型探索的自然结果——快速验证假设优先于架构完整。

## 6. 为什么不适合直接进入 V2 开发

**当前项目不建议直接作为 V2 产品化底座继续开发。**

继续堆 TTS 连续剧、背景音乐、自由对话、更多地图、更多居民，并不会自动让它变成一个成立的游戏。当前最大瓶颈已经从技术实现转移到游戏设计。

**具体原因：**

1. **游戏目标缺失** — 玩家每天为什么回来？V1 没有回答这个问题，继续加功能也不会自动产生目标
2. **架构不支撑产品迭代** — render.js 过重，状态边界不清，产品化开发会持续遭遇架构摩擦
3. **缺少游戏机制设计** — 当前是技术演示，不是游戏。直接堆功能会得到一个更贵的演示
4. **代码不可继承** — V1 代码适合做参考样机，不适合作为 V2 底座。下一项目应先完成设计，再决定是重构、复用模块还是新建项目

**V1 的正确价值：** 作为参考样机，证明 AI 可以驱动小镇生活闭环；作为经验沉淀，用于下一次更明确的设计。

## 7. 后续真正要做的游戏设计

在进入任何开发之前，必须先回答以下问题。这些是游戏设计问题，不是技术问题。

```
玩家是谁？
玩家每天为什么回来？
一天的核心循环是什么？
一周或一季的节奏是什么？
居民为什么值得玩家关心？
居民之间有什么关系和故事？
玩家选择如何影响长期后果？
小镇记忆如何影响未来事件？
AI 事件导演如何避免随机散乱？
哪些内容由 AI 生成，哪些必须由规则控制？
失败是什么？成长是什么？陪伴是什么？收集是什么？解锁是什么？
```

这些问题没有答案之前，任何继续开发（包括 V2）都是在不确定基础上的浪费。

## 8. 下一次 AI 游戏开发建议路线

### 阶段 0：游戏概念与情绪定位（1-2 周）

在写任何代码之前，先确定：
- 游戏给玩家什么感受？治愈？挑战？探索？陪伴？
- 目标用户是谁？
- 一句话描述核心体验

### 阶段 1：主循环设计（2-4 周）

回答：
- 玩家一天做什么？什么是"一天"的闭环？
- 玩家有目标吗？目标是什么？目标如何推进？
- 每天的短循环和每周/每季的长循环是什么？

产出：核心循环文档（不是代码，是流程图和规则）

### 阶段 2：居民与关系系统设计（2-3 周）

回答：
- 居民是什么？是一组数值还是有个性的角色？
- 居民之间有什么关系？如何推进？
- 玩家和居民的关系是什么？陪伴？帮助？引导？

### 阶段 3：事件导演规则设计（2-3 周）

回答：
- AI 事件导演的边界在哪里？什么必须由规则控制？
- 如何避免事件随机散乱？需要叙事弧线吗？
- 玩家选择的长期后果如何设计？不是记忆链路就够了的

### 阶段 4：记忆与长期后果设计（1-2 周）

回答：
- 小镇记忆和居民记忆如何影响未来事件？
- 哪些选择是"重要的"？哪些是"氛围的"？
- 长期后果的形式是什么？解锁新内容？改变外观？改变关系？

### 阶段 5：技术架构重新评估（1 周）

回答：
- 现有 V1 代码模块是否值得复用？domain 层？selectors？
- 是否需要引入游戏引擎？什么时候引入？
- 状态管理方案是否需要升级？

### 阶段 6：重新开发 MVP（持续）

带着完整设计文档重新开发，不是 V1 代码的延续。

**核心原则：先设计，再开发。先主循环，再功能堆叠。先规则边界，再 AI 生成。**

## 9. 哪些经验可以复用

以下 V1 经验在下一个项目中值得复用：

- **AI 作为事件导演** — M3 作为叙事导演生成事件的思路是有效的，下一个项目应继续深化
- **居民状态驱动任务** — 状态（体力、心情）影响行为的机制值得保留
- **选择写入记忆** — 选择记忆链路是有效的世界感增强手段
- **广播作为世界氛围层** — 广播文案是小镇"呼吸感"的重要来源
- **舞台演出优先于复杂系统** — 先让玩家看到，再让系统变复杂
- **轻量 Web 原型适合早期验证** — DOM/CSS 原型验证核心假设的成本远低于游戏引擎
- **测试脚本保护关键体验** — 自动化回归测试保护了关键体验不被破坏
- **API fallback 设计** — 无外部依赖时仍可运行是正确的产品决策

---

## 10. 哪些不应直接继承

以下 V1 实践不应在下一个项目中直接继承：

- **过重的 render.js** — UI 渲染和游戏状态不应混合在同一层
- **补丁式 UI 状态判断** — 多次修复积累了隐式约定，应在架构层面避免
- **缺少统一状态机的演出逻辑** — travel → task → feedback 的时序逻辑应显式化
- **模板对话的长期扩展方式** — 任务类型 × 场景矩阵的 fallback 不具备扩展性
- **事件、记忆、任务之间的松散耦合** — 下一个项目应在设计阶段就明确各模块边界
- **缺少玩法设计时直接堆功能的开发方式** — V1 是技术探索驱动，不是游戏设计驱动；下一个项目应反过来

---

## 结论

V1 是一次有效的技术探索，成功验证了"M3 可以作为小镇世界的规划者、叙事导演、广播员和记忆引用者"这一核心假设。

但 V1 不是游戏。它缺少游戏目标、缺少完整的居民关系系统、缺少故事结构、缺少长期后果机制。这些不是 V1 没做完的功能，而是 V1 没有去设计的问题。

继续在 V1 代码上堆功能不会解决这些问题。下一阶段的核心工作不是 V2 开发，而是游戏设计。

先设计，再开发。
